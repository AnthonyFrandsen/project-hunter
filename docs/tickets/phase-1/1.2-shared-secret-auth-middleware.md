# Phase 1.2 — Shared-Secret Auth Middleware

**Draft Number:** 1
**Ticket Status:** Draft — first pass, still being refined; not yet reviewed or implemented.

## Goal
Reject any incoming request that doesn't present a valid shared secret, per FR23, using the secret ticket 0.3 already generates and prints at startup.

## Description
- Ticket 0.3 already generates a fresh shared secret on every server startup (`config.sharedSecret`), printed to the console for the user to copy into the extension's configuration — never read from an env var, never persisted to disk between restarts (see `docs/tickets/phase-0/0.3-base-env-var-config-loading.md`). This ticket adds the middleware that actually enforces it on incoming requests; 0.3 only produced the value.
- Per `docs/open-questions.md` OQ2 (and its follow-up answer), the distribution flow is confirmed acceptable: the user manually copies the printed secret into the extension's options before loading it unpacked (Phase 11 documents the setup steps). No further product sign-off is needed on that mechanism — this ticket is purely the enforcement side.
- Middleware compares a token supplied on the incoming request against `config.sharedSecret`, rejecting with `401` when it's missing or doesn't match.
- Applies to the run-submission endpoint (ticket 1.3) and the status endpoint (ticket 1.4) — both carry or return data tied to a specific run. Whether it should also guard the existing `/health` check (ticket 0.2, carries no sensitive payload and predates this ticket) is an open question below.
- Where the token is supplied on the request (custom header vs. `Authorization` header vs. a body field) is an implementation detail, but this ticket is the source of truth for that choice — ticket 2.3 (extension scrape/POST logic) must send it exactly the way this ticket defines it, the same way ticket 0.3 became the source of truth for env var names.
- Token comparison should be constant-time (e.g. Node's `crypto.timingSafeEqual`) rather than plain `===`, to avoid a timing side-channel — a cheap hardening step worth taking given how low-cost it is.

## Acceptance Criteria
- [ ] A middleware rejects requests to protected endpoints with `401` when the shared-secret token is missing or doesn't match `config.sharedSecret`.
- [ ] Token comparison uses a constant-time comparison, not simple string equality.
- [ ] The token's transport mechanism (header name/format, or wherever it's decided to live) is documented in this ticket once chosen, since ticket 2.3 depends on it matching exactly.
- [ ] Middleware is applied to the run-submission (1.3) and status (1.4) endpoints.
- [ ] Tests cover: valid secret accepted, missing token rejected, wrong token rejected.

## Open Questions
- **OQ1.2-A:** Should `/health` (ticket 0.2) also require the shared secret, for consistency, or remain open since it's a low-stakes Docker/dev diagnostic with no sensitive payload? Leaning toward leaving it open, but not yet confirmed.
- **OQ1.2-B:** Exact transport mechanism for the token on incoming requests (custom header, e.g. `X-Hunter-Secret`, vs. `Authorization: Bearer <secret>`, vs. a body field) — needs to be picked here since ticket 2.3 will depend on it.
- This is a first-draft ticket — no review pass has happened yet. Additional open questions may surface once reviewed.
