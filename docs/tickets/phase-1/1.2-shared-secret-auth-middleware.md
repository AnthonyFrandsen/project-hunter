# Phase 1.2 — Shared-Secret Auth Middleware

**Draft Number:** 2
**Ticket Status:** Done — middleware implemented and tested; mounting it on the 1.3/1.4 endpoints themselves is deferred until those tickets add their routes (see Implementation Log)

## Goal
Reject any incoming request that doesn't present a valid shared secret, per FR23, using the secret ticket 0.3 already generates and prints at startup.

## Description
- Ticket 0.3 already generates a fresh shared secret on every server startup (`config.sharedSecret`), printed to the console for the user to copy into the extension's configuration — never read from an env var, never persisted to disk between restarts (see `docs/tickets/phase-0/0.3-base-env-var-config-loading.md`). This ticket adds the middleware that actually enforces it on incoming requests; 0.3 only produced the value.
- Per `docs/open-questions.md` OQ2 (and its follow-up answer), the distribution flow is confirmed acceptable: the user manually copies the printed secret into the extension's options before loading it unpacked (Phase 11 documents the setup steps). No further product sign-off is needed on that mechanism — this ticket is purely the enforcement side.
- Middleware compares a token supplied on the incoming request against `config.sharedSecret`, rejecting with `401` when it's missing or doesn't match.
- Applies to the run-submission endpoint (ticket 1.3) and the status endpoint (ticket 1.4) — both carry or return data tied to a specific run. Per OQ1.2-A (resolved), the existing `/health` endpoint (ticket 0.2) stays unauthenticated: it carries no sensitive payload, predates this ticket, and PRD §9 confirms no auth/origin checks are needed beyond the shared secret given personal, unpublished, localhost-only use.
- Where the token is supplied on the request (custom header vs. `Authorization` header vs. a body field) is left to the implementer per OQ1.2-B (resolved) — ticket 2.3 (extension scrape/POST logic) isn't being refined until after this ticket lands, so there's no dependency yet forcing an early pick. Whatever is chosen, this ticket becomes the source of truth for it and must be documented here once decided (see Acceptance Criteria), the same way ticket 0.3 became the source of truth for env var names — ticket 2.3 must send the token exactly the way this ticket documents.
  - **Decided (implementation-time):** a custom request header, `X-Hunter-Shared-Secret`, carrying the raw token value (no `Bearer` prefix or other wrapping). Exported as the `SHARED_SECRET_HEADER` constant from `server/src/middleware/require-shared-secret.ts` so ticket 2.3 (and any test code) can reference the literal instead of re-typing it. A custom header was chosen over `Authorization: Bearer` to avoid implying OAuth/JWT semantics this scheme doesn't have, and over a body field so the check works uniformly on both `GET /runs/status` (no body) and `POST /runs` (body already reserved for `listingText`, per ticket 1.3).
- Token comparison should be constant-time (e.g. Node's `crypto.timingSafeEqual`) rather than plain `===`, to avoid a timing side-channel — a cheap hardening step worth taking given how low-cost it is. Note `timingSafeEqual` throws if the two buffers differ in length, so comparing a raw variable-length request token directly against the secret would either crash (uncaught) or require a length pre-check that itself reintroduces a timing/branch side-channel. The straightforward fix: HMAC both the received token and `config.sharedSecret` (e.g. with a fixed local key/nonce, or simply SHA-256 both) to equal-length digests before calling `timingSafeEqual`, so the comparison never branches on input length.

## Implementation Log

**2026-07-31 — Middleware implemented and tested; endpoint wiring deferred (blocker below).**

High-level summary of what was built:
- `server/src/middleware/require-shared-secret.ts` exports `requireSharedSecret(config)`, an Express
  `RequestHandler` factory, and the `SHARED_SECRET_HEADER` constant (`"x-hunter-shared-secret"`).
  The returned middleware reads that header, and rejects with `401 { "error": "Unauthorized" }`
  when it's absent or doesn't match `config.sharedSecret`. Comparison hashes both the incoming
  token and the configured secret with SHA-256 (`node:crypto` `createHash`) to fixed-length
  digests, then compares those digests with `timingSafeEqual` — never calling `timingSafeEqual` on
  the raw, variable-length input, per the ticket's guidance.
- Token transport: a custom `X-Hunter-Shared-Secret` header (raw token, no `Bearer` prefix). Picked
  over `Authorization: Bearer` to not imply OAuth/JWT semantics, and over a body field so the same
  check works on both a bodyless `GET` and a `POST` whose body is already reserved for other
  payload (ticket 1.3's `listingText`). Documented in the Description above per OQ1.2-B.
- `server/src/routes/index.ts`'s `createRouter()` now mounts `requireSharedSecret(config)` via
  `router.use(...)` immediately after `healthRouter`. Because Express walks middleware in
  registration order and `healthRouter` only matches `GET /health` (returning a response and never
  calling `next()` for that path), `/health` never reaches the auth check, while *any* route
  registered on `router` after this line automatically requires the secret — no per-route wiring
  needed. `createApp`/`attachCoreMiddleware`'s config parameter widened from
  `Pick<Config, "ollamaEndpoint">` to `Pick<Config, "ollamaEndpoint" | "sharedSecret">` accordingly.
- Tests: `server/test/require-shared-secret.test.ts` covers the three required cases (valid secret
  accepted, missing token → 401, wrong token → 401) directly against the middleware, plus a
  same-length-mismatch case exercising the digest-before-`timingSafeEqual` path, plus an
  integration check that `/health` stays open through `createApp`. `server/test/app.test.ts`'s three
  pre-existing tests register ad-hoc routes *after* `createRouter` in the middleware chain (the same
  position a real protected route would occupy) and now had to start sending the shared-secret
  header to keep passing — which is itself a live demonstration that routes mounted after the auth
  middleware are protected by construction.

Blocker / course correction — AC "Middleware is applied to the run-submission (1.3) and status (1.4)
endpoints" could not be completed as literally stated: neither endpoint exists yet. Both tickets
1.3 and 1.4 are still `Ticket Status: Ready` with `Implementation Log: Not started` (checked before
starting this work). This is a ticket-ordering issue, not an environment blocker — nothing about the
sandboxed/Docker environment prevented progress. Resolution: rather than block entirely on 1.3/1.4
landing first, built the middleware and mounted it at the router level (see above) so that when 1.3
adds `POST /runs` and 1.4 adds `GET /runs/status`, mounting them via `router.use(...)` in
`createRouter` (the same pattern `healthRouter` already uses) picks up shared-secret enforcement
automatically, with no changes needed back in this ticket or theirs. Left the AC checkbox unchecked
rather than marking it done on a technicality, since it can't be verified end-to-end against the
real endpoints until 1.3/1.4 exist — whoever implements those tickets should confirm this AC once
their routes are mounted, and can flip the checkbox above at that point.
