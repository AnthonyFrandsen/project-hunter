# Phase 1.3 — FIFO Run Queue

**Draft Number:** 1
**Ticket Status:** Draft — first pass, still being refined; not yet reviewed or implemented.

## Goal
Accept run submissions over HTTP, hold them in a FIFO queue, and process them sequentially with a stubbed handler — no real pipeline logic yet — while continuing to accept new submissions without blocking (FR12).

## Description
- Add the run-submission endpoint (e.g. `POST /runs`, exact path TBD) that the extension will eventually call (ticket 2.3) with the scraped job listing text. For this ticket, the request body only needs to carry the listing text (per FR2) — no other payload shape is implied yet.
- On submission: generate a run ID, append the run to an in-memory FIFO queue with status `queued`, and respond immediately, without waiting for the run to complete. This is what "non-blocking accept of new runs while one is in progress" (FR12) means at the HTTP layer.
- A queue processor consumes runs one at a time, in submission order. For this ticket, "processing" a run means invoking a stub handler that simply waits (fixed or configurable delay) and then marks the run `done` — no real listing validation, tailoring, or file generation happens yet (those land in Phases 3, 5+, per `docs/roadmap.md`).
- Ticket 0.5 already built a stub Claude Code CLI client (`server/src/claude-cli.ts` / `claude-cli-stub.ts`) with a configurable artificial delay (`HUNTER_MOCK_OLLAMA_DELAY_MS`) specifically so surrounding pipeline logic like this queue could be exercised without a bespoke sleep of its own — reusing it here instead of writing a second delay mechanism is worth strong consideration (see Open Questions), though its listing/tailor-stage response shapes may be more than this ticket strictly needs.
- Queue and run-record state live in memory only — no persistence across server restarts, consistent with the shared secret's own no-persistence design (ticket 0.3).
- This ticket does not include the status/progress-reporting endpoint itself (that's ticket 1.4) — it only needs to expose whatever minimal internal state 1.4 will read (e.g. the current run and the pending queue).

## Acceptance Criteria
- [ ] A submission endpoint accepts a job listing text payload, enqueues a new run with a generated ID and `queued` status, and responds immediately without waiting for the run to finish.
- [ ] Runs are processed strictly in FIFO submission order, one at a time.
- [ ] Submitting a new run while another is queued or processing succeeds immediately (does not block on the in-progress run).
- [ ] The processing step for this ticket is a stub (fixed or configurable delay) that transitions a run `queued` → `running` → `done`, with no real listing-validation/tailoring logic.
- [ ] Queue state is in-memory only; no persistence across restarts is required.
- [ ] Tests cover: multiple submissions queue correctly, FIFO order is preserved, and submitting doesn't block on an in-progress run.
