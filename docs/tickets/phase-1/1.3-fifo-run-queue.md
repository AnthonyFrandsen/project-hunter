# Phase 1.3 — FIFO Run Queue

**Draft Number:** 2
**Ticket Status:** Done

## Goal
Accept run submissions over HTTP, hold them in a FIFO queue, and process them sequentially with a stubbed handler — no real pipeline logic yet — while continuing to accept new submissions without blocking (FR12).

## Description
- Add `POST /runs` (per OQ1.3-C, resolved) that the extension will eventually call (ticket 2.3) with the scraped job listing text. Request body: `{ "listingText": string }` — a single required field carrying the raw scraped text (FR2), nothing else (per OQ1.3-B, resolved).
- Validate that `listingText` is present and a non-empty string; respond `400` if it's missing, not a string, or empty. This is only a shallow type/presence check — judging whether the text is an actual valid job listing is FR14's job (Phase 3), not this ticket's.
- On a valid submission: generate a run ID (`crypto.randomUUID()` — built into Node, globally unique, no collision handling needed), append a run record to an in-memory FIFO queue with status `queued`, and respond immediately with `{ "id": string, "status": "queued" }` (per OQ1.3-B, resolved), without waiting for the run to complete. This is what "non-blocking accept of new runs while one is in progress" (FR12) means at the HTTP layer. The response deliberately omits a computed queue position — that would go stale the instant another run is submitted or finishes, so ticket 1.4's status endpoint is the one place that should compute queue depth, on demand, from live state.
- The run record stores at least `id`, `status`, and the submitted `listingText` — the text must be retained even though this ticket's stub handler doesn't read it, since Phases 3+ will need it once real processing lands; storing it now avoids revisiting this ticket later just to add it.
- A queue processor consumes runs one at a time, in submission order. For this ticket, "processing" a run means invoking a stub handler that transitions a run `queued` → `running` → `done`: it `await`s a plain local `sleep()` for `config.mockOllamaDelayMs` (per OQ1.3-A, resolved — see below) and then marks the run `done`. No real listing validation, tailoring, or file generation happens yet (those land in Phases 3, 5+, per `docs/roadmap.md`).
- Reuse is partial, not full: read the already-loaded `config.mockOllamaDelayMs` value (sourced from `HUNTER_MOCK_OLLAMA_DELAY_MS` via ticket 0.3/0.5's config module) and `await` a plain local `sleep()` with it in the queue processor, rather than calling through ticket 0.5's `createClaudeCliClient()`/`invoke()` seam. Reusing the *value* keeps delay configuration owned by exactly one env var and one piece of parsing/validation logic. Reusing the full CLI-client seam instead would force this ticket to fabricate inputs it has no real use for yet (a source resume path, output dir, base filename for a `tailor-resume` stage call) and inherit 0.5's stub file-write side effects — per 0.5's implementation log, that stage `writeFileSync`s real `.md`/`.docx` files to disk, which would leave spurious artifacts from a queue-mechanics ticket before Phases 3/5/6 exist to generate real ones.
- Queue and run-record state live in memory only — no persistence across server restarts, consistent with the shared secret's own no-persistence design (ticket 0.3).
- This ticket does not include the status/progress-reporting endpoint itself (that's ticket 1.4) — it only needs to expose whatever minimal internal state 1.4 will read (e.g. the current run and the pending queue).

## Acceptance Criteria
- [x] `POST /runs` accepts `{ "listingText": string }`; requests with a missing, non-string, or empty `listingText` are rejected with `400`.
- [x] A valid submission enqueues a new run (ID via `crypto.randomUUID()`, status `queued`, `listingText` retained on the record) and responds immediately with `{ "id": string, "status": "queued" }`, without waiting for the run to finish or computing a queue position.
- [x] Runs are processed strictly in FIFO submission order, one at a time.
- [x] Submitting a new run while another is queued or processing succeeds immediately (does not block on the in-progress run).
- [x] The processing step for this ticket is a stub that transitions a run `queued` → `running` → `done` by `await`-ing a local `sleep()` for `config.mockOllamaDelayMs`, with no real listing-validation/tailoring logic and no dependency on ticket 0.5's CLI-client seam.
- [x] Queue state is in-memory only; no persistence across restarts is required.
- [x] Tests cover: a missing/empty `listingText` is rejected with `400`, multiple valid submissions queue correctly, FIFO order is preserved, and submitting doesn't block on an in-progress run.

Prior-draft open questions were answered and folded into the Description/Acceptance Criteria above:
- OQ1.3-A (should the stub reuse ticket 0.5's mock Claude CLI client/delay config?) — answered: partial reuse of the `config.mockOllamaDelayMs` value only, via a plain local `sleep()`, not the full CLI-client seam.
- OQ1.3-B (exact request/response payload shape) — answered: request `{ "listingText": string }`, response `{ "id": string, "status": "queued" }`, no computed queue position.
- OQ1.3-C (endpoint path/method naming) — answered: `POST /runs` (plural, collection-style), pairing with ticket 1.4's likely `GET /runs/:id`.

This refinement pass turned up three further implementation nuances worth calling out (folded into the Description/Acceptance Criteria above rather than left as open questions, since each has a clear recommended resolution):
- Run ID generation was previously unspecified. Recommendation applied: `crypto.randomUUID()` — a Node built-in, globally unique, no extra dependency or collision handling needed.
- `listingText` presence/type validation on submission was previously unspecified. Recommendation applied: reject with `400` if missing, non-string, or empty. This stays a shallow check only — judging whether the text is an actual valid job listing is FR14's job (Phase 3), not this ticket's.
- Whether the run record needs to retain the submitted `listingText` (beyond `id`/`status`) was previously unaddressed. Recommendation applied: yes — Phases 3+ will need the original text once real processing lands, and storing it now avoids reopening this ticket later just to add it.

No open questions remain that block starting implementation.

## Implementation Log

**2026-07-31 — Implemented and verified.**

High-level summary of what was built:
- `server/src/run-queue.ts` (new) is the FIFO queue module. `createRunQueue(config)` closes over an
  in-memory `Run[]` array (`{ id, status, listingText }`) and returns a small interface:
  `submit(listingText)` pushes a `queued` run, kicks the processor, and returns
  `{ id, status: "queued" }` synchronously; `getCurrentRun()` returns whichever run is `running`, or
  — once it finishes — stays pointed at that same (now `done`) record until the processor picks up
  the next `queued` run, which is exactly the "current run" semantics ticket 1.4 will need
  (in-progress run, or most-recently-finished run, retained rather than evicted); `getQueuedRuns()`
  returns the runs still waiting, in FIFO order, for 1.4's `queueDepth`. The processor itself is a
  simple non-reentrant loop (`processing` flag) that takes the next `queued` run, flips it to
  `running`, `await`s a local `sleep(config.mockOllamaDelayMs)`, flips it to `done`, then
  immediately looks for the next `queued` run — so a run already waiting behind the current one
  starts the instant its predecessor finishes, with no extra event needed to kick it off.
- `server/src/routes/runs.ts` (new) adds `POST /runs`. Validates `listingText` is present, a
  `string`, and non-empty (shallow presence/type check only, per the ticket — no listing-quality
  judgment); responds `400` with `{ error: string }` on failure. On success, delegates straight to
  `runQueue.submit()` and responds `201` with its `{ id, status }` result.
- `server/src/routes/index.ts` now builds one `RunQueue` per `createRouter()` call (i.e. one per
  app/server instance) via `createRunQueue(config)`, and mounts `runsRouter(runQueue)` after the
  `requireSharedSecret` middleware, alongside the existing `/health` router. Keeping the queue
  instance at the router level (rather than inside `runs.ts`) is deliberate: ticket 1.4's
  `GET /runs/status` will read the same instance, so both routes need to share it rather than each
  constructing their own.
- `server/src/app.ts`'s `Pick<Config, ...>` parameter types widened to include
  `mockOllamaDelayMs`, since it now flows from `index.ts`'s real `Config` down through
  `createApp`/`attachCoreMiddleware`/`createRouter` to `createRunQueue`.
- Response status code for a successful submission wasn't pinned down by the ticket (only the body
  shape was specified) — used `201 Created`, since the request creates a new run resource; a `400`
  is used for validation failures, consistent with the rest of the router's error conventions.
- Tests: `server/test/run-queue.test.ts` (new) unit-tests the queue module directly — unique/UUID
  IDs, `listingText` retention, the `queued` → `running` → `done` transition timed against
  `config.mockOllamaDelayMs`, non-blocking submission (second `submit()` call returns in <50ms
  while the first is still "processing" with a 1000ms delay), strict FIFO ordering across three
  queued runs (asserted at checkpoints timed relative to the configured delay), and that the most
  recently finished run stays `getCurrentRun()` once the queue drains. `server/test/runs.test.ts`
  (new) covers the same behavior at the HTTP layer: `400` on missing/non-string/empty
  `listingText`, `201` with `{ id, status: "queued" }` on success, that the route still requires the
  shared secret like every other route mounted after ticket 1.2's middleware, and that a second
  `POST /runs` returns immediately (<500ms) while a first run is mid-flight with a 1000ms stub
  delay. `server/test/app.test.ts` and `server/test/require-shared-secret.test.ts` had their inline
  config fixtures updated to include `mockOllamaDelayMs: 0`, since `attachCoreMiddleware`'s
  parameter type now requires it.
