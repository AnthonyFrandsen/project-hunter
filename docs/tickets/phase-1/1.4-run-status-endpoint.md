# Phase 1.4 — Run-Status Endpoint

**Draft Number:** 1
**Ticket Status:** Draft — first pass, still being refined; not yet reviewed or implemented.

## Goal
Expose an endpoint reporting the active run's progress step and queue depth, per FR26, supporting both the popup's 30-second polling (FR4/FR5) and reconnect-on-reopen (FR24).

## Description
- Per `docs/open-questions.md` OQ3/OQ4, transport is polling every 30 seconds (extension-side work lands in tickets 2.5/2.6), and the same endpoint must support popup reconnect: it needs to reflect current state on each call rather than a stream of deltas, so a popup that was closed and reopened mid-run can query it fresh and get an accurate picture (FR24).
- Add a `GET` endpoint (e.g. `GET /runs/status` or `GET /runs/:id`, exact shape TBD — see Open Questions) backed by the in-memory run/queue state from ticket 1.3. The response should report, at minimum, the active run's current progress step and the current queue depth.
- PRD §5 defines five canonical, user-facing progress-step labels: "Parsing job listing" → "Tailoring content" → "Checking page length" → "Generating .docx/.pdf/.md" → "Done". This ticket's own pipeline is still a stub (ticket 1.3's sleep-based processing) — no real stage transitions exist yet, so how the endpoint should represent progress in the meantime is an open question below rather than assumed.
- Whether status is looked up per-run (by an ID returned from ticket 1.3's submission response, so a reopened popup can find its own submitted run wherever it landed) or is a single global "whatever's currently happening" endpoint is unresolved — see Open Questions. This choice also directly affects how precisely ticket 2.9's reconnect logic can be scoped.

## Acceptance Criteria
- [ ] A `GET` endpoint reports the active run's current progress step and the current queue depth.
- [ ] The endpoint reflects current state on each call (suitable for both periodic polling and one-off reconnect queries), not a delta/stream.
- [ ] The response shape is decided and documented here so tickets 2.5/2.6/2.9 can be built against it without re-deriving it.
- [ ] Tests cover: status while the queue is empty, status with one run processing, and status with additional runs queued behind it (correct depth reported).

## Open Questions
- **OQ1.4-A:** Per-run lookup (status of a specific run ID, so a reopened popup can find its own submitted run) vs. a single global "current state" endpoint (simpler, but ambiguous once multiple runs are queued from the same session) — needs a decision before ticket 2.9's reconnect logic can be scoped precisely.
- **OQ1.4-B:** Since this phase's pipeline is only a stub sleep (ticket 1.3), what progress-step label(s) should the endpoint report while a stub run is "processing"? Candidate options: report only coarse status (`queued`/`running`/`done`) until Phases 3–8 land their real stages and start setting the five canonical §5 labels themselves; or have the stub itself emit a placeholder label. Needs a decision so ticket 2.5's step-rendering isn't built against a shape that changes later.
- **OQ1.4-C:** Exact response JSON field names/shape is a placeholder pending review.
- This is a first-draft ticket — no review pass has happened yet. Additional open questions may surface once reviewed.
