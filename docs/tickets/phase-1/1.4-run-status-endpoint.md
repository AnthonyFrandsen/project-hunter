# Phase 1.4 — Run-Status Endpoint

**Draft Number:** 3
**Ticket Status:** Ready

## Goal
Expose an endpoint reporting the active run's progress step and queue depth, per FR26, supporting both the popup's 30-second polling (FR4/FR5) and reconnect-on-reopen (FR24).

## Description
- Per `docs/open-questions.md` OQ3/OQ4, transport is polling every 30 seconds (extension-side work lands in tickets 2.5/2.6), and the same endpoint must support popup reconnect: it needs to reflect current state on each call rather than a stream of deltas, so a popup that was closed and reopened mid-run can query it fresh and get an accurate picture (FR24).
- Add `GET /runs/status`, backed by the in-memory run/queue state from ticket 1.3. Per OQ1.4-A's resolution, this is a single global "current state" endpoint, not a per-run lookup: the popup never needs to distinguish between runs by ID, only to know what the currently-processing run's step is and how deep the queue is behind it. It responds:
  ```json
  {
    "step": "string | null",
    "queueDepth": "number"
  }
  ```
  - `step` is `null` only in the endpoint's initial state, before any run has ever been submitted for the lifetime of the server process — this is the signal the popup uses to show the run-submittal button instead of a progress display. Once the first run is submitted, `step` is one of PRD §5's five canonical labels and never reverts to `null` again (see OQ1.4-D's resolution below): it reflects whichever run is "current."
  - "Current" run (per OQ1.4-D's resolution) is the run currently in progress (queued or running), or — if none is in progress — the most recently finished run, until a new run is submitted. Concretely: while a run is queued/running, `step` reports its in-progress label; the moment that run finishes, `step` flips to `"Done"` and stays `"Done"` — regardless of how many poll intervals pass — until the next `POST /runs` call starts a new run, at which point `step` resets to that new run's in-progress label. This makes `"Done"` reliably observable by the popup's 30-second polling (FR4/FR5) without racing the poll interval against a run that finishes and is superseded between polls, and gives ticket 2.7 a stable "step transitioned to `Done`" condition to trigger its end-of-run notification (FR6) on.
  - `queueDepth` is the count of runs still waiting behind the one currently processing (0 once only one run remains queued/running, and 0 while `step` is `"Done"` or `null`), computed on demand from ticket 1.3's live queue state on every request — never cached — matching FR5 and consistent with ticket 1.3's own decision to omit a computed queue position from its submission response for the same staleness reason.
- PRD §5 defines five canonical, user-facing progress-step labels: "Parsing job listing" → "Tailoring content" → "Checking page length" → "Generating .docx/.pdf/.md" → "Done". This ticket's own pipeline is still a stub (ticket 1.3's sleep-based processing) — no real stage transitions exist yet. Per OQ1.4-B's resolution, the endpoint reports `"Parsing job listing"` as `step` for any run that is currently running: it's the only one of the five labels whose precondition (text submitted, nothing produced yet) actually holds for a run that's merely sleeping. `"Done"` is reported as-is once the stub's `queued` → `running` → `done` transition (ticket 1.3) completes. Real stage transitions land in Phases 3–8, which will set `step` to the other three intermediate labels as appropriate; this ticket's shape doesn't change when they do.
- Implementation nuance: reporting `"Done"` for the most recently finished run requires the run-record store to retain that record after it transitions to `done`, rather than evicting it once the queue processor moves on. Ticket 1.3's Description scopes its exposed internal state loosely ("whatever minimal internal state 1.4 will read, e.g. the current run and the pending queue"), which is compatible with this but doesn't commit to it explicitly. Recommendation applied: no change to ticket 1.3 needed — this ticket's implementer keeps a reference to the most recently finished run (or simply leaves finished records in place rather than removing them from whatever structure 1.3 uses) alongside the pending-queue/current-run state 1.3 already exposes. This is within-process, in-memory retention only, consistent with 1.3's no-persistence-across-restarts scope.

## Acceptance Criteria
- [ ] `GET /runs/status` reports `{ "step": string | null, "queueDepth": number }`, reflecting live state on every call (suitable for both periodic polling and one-off reconnect queries), not a delta/stream.
- [ ] `step` is `null` only before any run has ever been submitted; otherwise it is `"Parsing job listing"` (this ticket's stub placeholder — see Description) for the currently-processing run, or `"Done"` for the most recently finished run once no run is in progress.
- [ ] Once a run finishes, `step` reports `"Done"` and stays `"Done"` across any number of subsequent polls until the next `POST /runs` call starts a new run, at which point `step` resets to `"Parsing job listing"` for the new run.
- [ ] `queueDepth` reports the number of runs still waiting behind the one currently processing, computed live from ticket 1.3's queue state on each request (not cached on the run record); it is `0` whenever `step` is `"Done"` or `null`.
- [ ] Tests cover: status before any run has been submitted (`step: null`, `queueDepth: 0`), status with one run processing (`step: "Parsing job listing"`, `queueDepth: 0`), status with additional runs queued behind it (`queueDepth` reflects the correct count), status after a run finishes with nothing else queued (`step: "Done"`, `queueDepth: 0`, and this persists across repeated polls), and status after a subsequent run is submitted following a `"Done"` state (`step` resets to `"Parsing job listing"`).

## Open Questions
Prior-draft open questions were answered and folded into the Description/Acceptance Criteria above:
- OQ1.4-A (per-run lookup vs. a single global "current state" endpoint) — answered: global, `GET /runs/status`. The popup only ever needs the currently-processing run's step and the queue depth behind it, never a specific run by ID, so per-run lookup was rejected in favor of the simpler shape.
- OQ1.4-B (what progress-step label a stubbed run should report) — answered: `"Parsing job listing"`, drawn from the real §5 vocabulary rather than an invented coarse status, so ticket 2.5's rendering doesn't need to change once Phases 3–8 land real stage transitions.
- OQ1.4-C (exact response JSON shape) — answered: `{ "step": "string | null", "queueDepth": "number" }`. No `id`/`status` fields — the popup doesn't query by run ID, so the response is reduced to only what it renders.
- OQ1.4-D (how the popup ever observes the terminal `"Done"` step, given a run stops being "queued or running" the moment it finishes) — decided: the endpoint's notion of the "current" run is the run in progress, or — if none is in progress — the most recently finished run, until a new run is submitted. `step` reports `"Done"` for a just-finished run and keeps reporting it across any number of polls until the next `POST /runs` call starts a new run. Folded into the Description and Acceptance Criteria above.

This refinement pass also resolved one implementation nuance inline (no product decision needed, so it wasn't left open): whether ticket 1.3's exposed state needs to retain finished run records for 1.4 to report `"Done"` from. Resolved: yes, 1.4's implementer keeps a reference to the most recently finished run rather than letting it be evicted; ticket 1.3's Description already scopes its exposed state loosely enough to accommodate this without requiring changes to 1.3 itself. See the "Implementation nuance" bullet in the Description.

No open questions remain that block starting implementation.
