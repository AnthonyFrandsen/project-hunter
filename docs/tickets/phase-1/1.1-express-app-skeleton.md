# Phase 1.1 — Express App Skeleton

**Draft Number:** 2
**Ticket Status:** Done

## Goal
Extend the minimal Express app from ticket 0.2 into a structured skeleton that the rest of Phase 1 (auth middleware, run/queue endpoints, status endpoint) can attach to cleanly, satisfying FR9 in full.

## Description
- A baseline already exists from earlier phases: `server/src/app.ts` exports `createApp()` with a single `GET /health` route (ticket 0.2), and `server/src/index.ts` calls `createApp(config).listen(10105)` after `loadConfig()` succeeds (ticket 0.3). FR9's literal requirement ("runs ... listening on `http://localhost:10105`") is already satisfied by that baseline — this ticket is about restructuring for what's coming next, not standing the server up from scratch.
- Add JSON body-parsing middleware (e.g. `express.json()`), since ticket 1.3's run-submission endpoint needs to parse a JSON payload (the scraped job listing text) from the extension.
- Introduce a clear routing structure (e.g. a `routes/` module, or an internal `Router` mounted onto the app) so that tickets 1.2 (auth middleware), 1.3 (run submission/queue), and 1.4 (status endpoint) each have an obvious, consistent place to add their handlers, rather than every route living in one growing flat file.
- Add a generic error-handling middleware (Express's 4-arg error-handler signature) that catches unhandled thrown/rejected errors from route handlers and responds with a generic 500, rather than crashing the process or leaking a stack trace to the caller. This is foundational plumbing only — it is *not* Phase 9's distinct-error-taxonomy work (§7's six named failure types); Phase 9 owns mapping specific pipeline failures to specific user-facing errors. Per OQ1.1-A (resolved): this handler is permanent, not a placeholder Phase 9 later replaces — Phase 9 layers its named failure types on top of it, and this middleware remains the catch-all beneath that layer for *unforeseen* errors only (bugs, unhandled edge cases), not the accounted-for failure paths Phase 9 will give specific names to.
- Out of scope for this ticket: the shared-secret auth check (1.2), the run-submission/queue endpoints themselves (1.3), and the status endpoint (1.4) — this ticket only prepares the structure they'll attach to.

## Implementation Log

**2026-07-31 — Implemented and verified.**

High-level summary of what was built:
- `server/src/app.ts`'s `/health` handler moved into a new `routes/` module
  (`server/src/routes/health.ts`, `healthRouter(config)`) and a top-level aggregator
  (`server/src/routes/index.ts`, `createRouter(config)`) that mounts it. This is the "obvious,
  consistent place" the ticket calls for: 1.2's auth middleware, 1.3's `POST /runs`, and 1.4's
  `GET /runs/status` each get their own `routes/*.ts` module mounted the same way, rather than
  growing the one flat file further.
- `server/src/middleware/error-handler.ts` adds a generic 4-arg Express error handler
  (`errorHandler`): logs the error via `console.error`, and responds `500 { "error": "Internal
  server error" }` unless a response was already sent (in which case it delegates to Express's
  default handler via `next(err)` rather than trying to double-send). This is the permanent
  catch-all the ticket and OQ1.1-A describe — Phase 9 layers named failure types on top of it
  later, not a replacement.
- `server/src/app.ts`'s `createApp()` now composes three pieces in order: `express.json()` +
  `createRouter(config)` (via a small `attachCoreMiddleware()` helper), then `errorHandler` (via
  `attachErrorHandler()`). Splitting `createApp()` into `attachCoreMiddleware()` /
  `attachErrorHandler()` (both exported) was a course correction from the plan of testing purely
  through `createApp()`: Express dispatches middleware in registration order, so a test route
  added to the object `createApp()` returns would land *after* the already-mounted error handler
  in the stack and never reach it. Exporting the two composition steps lets tests build a
  realistic app (`attachCoreMiddleware` → test-only route → `attachErrorHandler`) that exercises
  the exact same middleware instances used in production, in the same order, without adding any
  test-only hook to `createApp()` itself or to any production route.
- Tests: added `server/test/app.test.ts` covering JSON body-parsing (`POST` with a JSON body is
  parsed into `req.body` before the handler runs) and the error handler (a route that throws
  synchronously, and one whose returned promise rejects, both get a `500 { error: string }`
  response instead of crashing the process — Express 5 forwards async rejections to error
  middleware automatically, so no wrapper was needed). `server/test/index.test.ts` (the existing
  `/health` test) was left unchanged and still passes unmodified, confirming the route survived
  the move.
- Verification: `npm run build` (tsc project build) and `npm test` (mocha, 26 tests) both pass
  cleanly from inside the sandboxed dev container; `npm run lint` (biome) reports only two
  pre-existing infos in an unrelated smoke-test script, nothing in the touched files.

No blockers or open questions encountered. This ticket is pure in-process Express wiring exercised
via ephemeral-port HTTP tests inside the sandbox — it did not require standing up the
Docker Compose stack or reaching from the Windows host, so (unlike tickets 0.2/0.4) no host-side
verification step was needed here.
