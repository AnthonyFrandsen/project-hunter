# Phase 1.1 — Express App Skeleton

**Draft Number:** 1
**Ticket Status:** Draft — first pass, still being refined; not yet reviewed or implemented.

## Goal
Extend the minimal Express app from ticket 0.2 into a structured skeleton that the rest of Phase 1 (auth middleware, run/queue endpoints, status endpoint) can attach to cleanly, satisfying FR9 in full.

## Description
- A baseline already exists from earlier phases: `server/src/app.ts` exports `createApp()` with a single `GET /health` route (ticket 0.2), and `server/src/index.ts` calls `createApp(config).listen(10105)` after `loadConfig()` succeeds (ticket 0.3). FR9's literal requirement ("runs ... listening on `http://localhost:10105`") is already satisfied by that baseline — this ticket is about restructuring for what's coming next, not standing the server up from scratch.
- Add JSON body-parsing middleware (e.g. `express.json()`), since ticket 1.3's run-submission endpoint needs to parse a JSON payload (the scraped job listing text) from the extension.
- Introduce a clear routing structure (e.g. a `routes/` module, or an internal `Router` mounted onto the app) so that tickets 1.2 (auth middleware), 1.3 (run submission/queue), and 1.4 (status endpoint) each have an obvious, consistent place to add their handlers, rather than every route living in one growing flat file.
- Add a generic error-handling middleware (Express's 4-arg error-handler signature) that catches unhandled thrown/rejected errors from route handlers and responds with a generic 500, rather than crashing the process or leaking a stack trace to the caller. This is foundational plumbing only — it is *not* Phase 9's distinct-error-taxonomy work (§7's six named failure types); Phase 9 owns mapping specific pipeline failures to specific user-facing errors.
- Out of scope for this ticket: the shared-secret auth check (1.2), the run-submission/queue endpoints themselves (1.3), and the status endpoint (1.4) — this ticket only prepares the structure they'll attach to.
