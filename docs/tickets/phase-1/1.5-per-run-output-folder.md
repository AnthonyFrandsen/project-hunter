# Phase 1.5 — Per-Run Timestamped Output Folder Creation

**Draft Number:** 3
**Ticket Status:** Ready

## Goal
Create a fresh, correctly named timestamped subfolder under the configured output base directory for every run, per FR11.

## Description
- Ticket 0.3 already validates and creates the base folder itself (`HUNTER_OUTPUT_DIR`) at startup. This ticket is about the next level down: a per-run subfolder, created when a run begins processing (ticket 1.3), that later phases will write into (ticket 3.3's `job-listing.md`, tickets 5.3/6.x's tailored outputs, ticket 8.x's artifact assembly).
- Folder naming: timestamped, per `docs/prd.md` §8 ("each run creates a timestamped subfolder"), using local time (not UTC) in an ISO-8601-derived format with colons swapped for filesystem-unsafe dashes: `YYYY-MM-DDTHH-mm-ss` (e.g. `2026-07-30T14-32-05`). This is the smallest possible deviation from the PRD's own "timestamped subfolder" phrasing (§8), keeps the folder lexicographically sortable in chronological order, and stays human-readable when the user browses `HUNTER_OUTPUT_DIR` manually in Windows Explorer (the PRD's target platform) — versus a dense compact-digit alternative (e.g. `20260730-143205`) that requires manually counting digits to parse. Local time avoids requiring the user to do timezone math against their own wall clock, appropriate for a single-user local desktop app.
- Creation should happen as part of a run transitioning into processing (ticket 1.3's queue processor advancing a run from `queued` to `running`), not at submission/enqueue time — a run still sitting in the queue shouldn't have a folder created before its turn. The timestamp used for the folder name is captured at this same moment (the start of processing), not at submission time.
- This ticket only creates the folder; it doesn't write any files into it yet (that's later phases' job). A reasonable way to verify this ticket in isolation is confirming the folder exists on disk once a (stubbed) run reaches `running`/`done`.
- Collision handling — two runs' start timestamps landing in the same instant (e.g. same second) — is not addressed with a disambiguating suffix (e.g. `-2`). Ticket 1.3's queue processor is strictly sequential: a run's `queued` → `running` transition (and thus its folder-creation call) only fires after the previous run has fully finished (`running` → `done`), and per-run processing always takes at least `config.mockOllamaDelayMs` today (and, in later phases, however long the real Ollama/Claude Code CLI invocation takes — potentially minutes, per FR15's no-enforced-timeout allowance). Two folder-creation timestamps landing in the same second is therefore excluded by the processing model itself, not just unlikely. Instead of suffix-disambiguation logic for a scenario the FIFO model already rules out, the folder is created with a non-recursive `fs.mkdirSync(path)` (unlike ticket 0.3's base-dir creation, which intentionally uses `{ recursive: true }` for idempotency): if the invariant were ever violated — e.g. by a future refactor — this throws `EEXIST` instead of silently reusing or overwriting a previous run's output folder, surfacing the violation as an error rather than corrupting a prior run's output.
- Per OQ1.5-C (resolved): if `mkdirSync` throws `EEXIST`, the queue processor adds no try/catch around the call and no new run status to record the failure — the error is left to propagate uncaught. No code in this ticket routes the error anywhere; it's the *absence* of handling that is the deliberate choice. Note the mechanism this actually engages: ticket 1.3's `POST /runs` handler always responds immediately without waiting for the run to finish (FR12's non-blocking requirement), so a later-queued run's `queued` → `running` advancement — and thus its folder-creation call — happens outside any single HTTP request's call stack. Ticket 1.1's generic Express error-handling middleware only intercepts errors surfaced within an active request/response cycle (a synchronous throw in a route handler, or an error passed to `next(err)`); it has nothing to attach to when the queue processor throws between requests. In practice this throw becomes an unhandled promise rejection (the queue processor is expected to be `async`, per ticket 1.3's `await sleep(...)`), which by default crashes the Node process (Node ≥15 behavior) rather than being caught by any Express middleware. The net effect — a loud process crash with a stack trace, no silent stall, no speculative `failed` run status — matches this ticket's original recommendation; only the mechanism differs from what was first assumed.

## Acceptance Criteria
- [ ] A new timestamped subfolder is created under `HUNTER_OUTPUT_DIR` when a run begins processing.
- [ ] The folder name matches the format `YYYY-MM-DDTHH-mm-ss` in local time (e.g. `2026-07-30T14-32-05`), filesystem-safe on Windows.
- [ ] Folder creation happens at the start of processing, not at submission/enqueue time; the timestamp is captured at that same moment.
- [ ] Folder creation uses a non-recursive `fs.mkdirSync(path)` (not `{ recursive: true }`), so a same-path collision throws `EEXIST` rather than silently succeeding.
- [ ] The created folder path is attached to the in-memory run record (ticket 1.3) so later phases can locate it.
- [ ] No try/catch is added around the `mkdirSync` call in ticket 1.3's queue processor, and no new run status (e.g. `failed`) is introduced to record a collision — the `EEXIST` throw is left to propagate uncaught, crashing the server process rather than leaving the run stuck in `running`.
- [ ] Tests cover: the folder is created with the expected naming pattern; the folder is not created merely because a run was enqueued (only once it starts processing); a pre-existing folder at the same path causes `mkdirSync` to throw rather than being silently reused.

## Open Questions
Prior-draft open questions were answered and folded into the Description/Acceptance Criteria above:
- OQ1.5-A (exact timestamp format for the folder name) — answered: `YYYY-MM-DDTHH-mm-ss` in local time (e.g. `2026-07-30T14-32-05`), an ISO-8601-derived format with colons swapped for dashes.
- OQ1.5-B (whether same-second collisions need a disambiguating suffix) — answered: no suffix needed, since ticket 1.3's strictly sequential FIFO processing excludes same-second collisions by construction; a non-recursive `fs.mkdirSync(path)` is used as a zero-cost safety net that throws `EEXIST` if the invariant is ever violated (e.g. by a future refactor), rather than silently overwriting a prior run's folder.
- OQ1.5-C (should a thrown `EEXIST` be caught, and does the run model need a `failed` status?) — decided: no. The queue processor adds no try/catch and ticket 1.3's run model gains no `failed` status in this ticket; the error is left to propagate uncaught, which is preferable to either silently reusing a folder or leaving a run stuck in `running` forever and stalling the FIFO queue behind it.
  - This refinement pass corrected the reasoning behind that decision rather than its outcome. The decision as first recorded assumed the throw would be "caught by the generic error handling middleware specified by ticket 1.1" — but that middleware (per ticket 1.1) only intercepts errors surfaced within an active HTTP request/response cycle, and ticket 1.3's queue processor advances a later-queued run to `running` (and thus calls `mkdirSync`) outside any single request's call stack, since `POST /runs` always responds immediately without waiting for the run to finish (FR12). There is no in-flight request for ticket 1.1's middleware to attach to at that point, so it cannot be what catches this error. What actually happens at runtime: the throw becomes an unhandled promise rejection (the queue processor is `async`, per ticket 1.3's `await sleep(...)`), which crashes the Node process by default (Node ≥15) — the same loud-failure outcome this ticket's prior draft recommended, just via Node's default unhandled-rejection behavior rather than Express middleware. No code changes to this ticket's acceptance criteria follow from this correction (no try/catch or `next(err)` wiring is added either way) — it only corrects the explanation on record.
