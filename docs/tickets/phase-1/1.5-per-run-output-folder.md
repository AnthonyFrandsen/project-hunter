# Phase 1.5 — Per-Run Timestamped Output Folder Creation

**Draft Number:** 1
**Ticket Status:** Draft — first pass, still being refined; not yet reviewed or implemented.

## Goal
Create a fresh, correctly named timestamped subfolder under the configured output base directory for every run, per FR11.

## Description
- Ticket 0.3 already validates and creates the base folder itself (`HUNTER_OUTPUT_DIR`) at startup. This ticket is about the next level down: a per-run subfolder, created when a run begins processing (ticket 1.3), that later phases will write into (ticket 3.3's `job-listing.md`, tickets 5.3/6.x's tailored outputs, ticket 8.x's artifact assembly).
- Folder naming: timestamped, per `docs/prd.md` §8 ("each run creates a timestamped subfolder"). The exact format (e.g. ISO 8601 with filesystem-safe separators, since `:` isn't a valid character in Windows paths — the PRD's target platform) needs to be decided; see Open Questions.
- Creation should happen as part of a run transitioning into processing (ticket 1.3's queue processor advancing a run from `queued` to `running`), not at submission/enqueue time — a run still sitting in the queue shouldn't have a folder created before its turn.
- This ticket only creates the folder; it doesn't write any files into it yet (that's later phases' job). A reasonable way to verify this ticket in isolation is confirming the folder exists on disk once a (stubbed) run reaches `running`/`done`.
- Collision handling — two runs' start timestamps landing in the same instant (e.g. same second) — should at least be considered, however unlikely given ticket 1.3's strictly sequential FIFO processing; see Open Questions.

## Acceptance Criteria
- [ ] A new timestamped subfolder is created under `HUNTER_OUTPUT_DIR` when a run begins processing.
- [ ] The folder-naming format is filesystem-safe on Windows and documented here once decided.
- [ ] Folder creation happens at the start of processing, not at submission/enqueue time.
- [ ] The created folder path is attached to the in-memory run record (ticket 1.3) so later phases can locate it.
- [ ] Tests cover: the folder is created with the expected naming pattern; the folder is not created merely because a run was enqueued (only once it starts processing).

## Open Questions
- **OQ1.5-A:** Exact timestamp format for the folder name (e.g. `2026-07-30T14-32-05` vs. a simpler `20260730-143205`) — needs a decision; must avoid characters invalid in Windows paths (`:`).
- **OQ1.5-B:** Collision handling if two runs' start timestamps land in the same second — is a disambiguating suffix (e.g. `-2`) needed, or is ticket 1.3's strictly sequential FIFO processing sufficient to make this practically impossible? Leaning toward "not needed," but not yet confirmed.
- This is a first-draft ticket — no review pass has happened yet. Additional open questions may surface once reviewed.
