# Phase 0.2 — Docker Compose & Ollama Reachability

**Draft Number:** 4
**Ticket Status:** Done — implementation complete, Docker-execution verified on the Windows host (see Implementation Log)

## Goal
Get a running Docker Compose stack for the server that can reach the native Windows-hosted Ollama instance, before any product logic exists.

## Description
- Write a `Dockerfile` for the `server/` package (Node/TypeScript/Express), building on the workspace scaffolding from ticket 0.1. Base image Node version should match whatever pinning mechanism 0.1 lands on (`.nvmrc`/`engines`/both).
- Write a `docker-compose.yml` that builds/runs the server container. Only the `server/` service is in scope here — no other services exist in the stack yet.
- Ollama runs natively on the Windows host, not inside the Compose stack — the container must reach it via `host.docker.internal`. No `extra_hosts` entry is needed: PRD §9 confirms Windows-only as the target platform, and Docker Desktop for Windows resolves `host.docker.internal` out of the box (the `extra_hosts: ["host.docker.internal:host-gateway"]` workaround is only needed on native Linux Docker Engine).
- Add a minimal health-check endpoint to the Express app (e.g. `GET /health`) that, when hit, makes a request to the host-side Ollama instance and reports whether it succeeded. This is the mechanism that proves connectivity — no ad hoc `docker compose exec` commands or throwaway scripts needed. The endpoint targets Ollama's default port, hardcoded as `http://host.docker.internal:11434` — ticket 0.3 owns replacing this hardcoded value with the real config-driven Ollama endpoint env var once its config loader lands. This is a raw network-reachability check only — it is *not* the real OpenAI-compatible-endpoint smoke test, which is ticket 0.4's job once 0.3's config loading exists.
- Since the health endpoint means the Express app now listens on something, `docker-compose.yml` should publish the server's eventual port (`10105` per PRD §4).
- This ticket does not stand up any further Express routes/logic beyond the health endpoint, and does not wire the Claude Code CLI working-directory volume mount described in PRD §4 item 3 — that belongs to Phase 4.

## Implementation Log

**2026-07-28 — Implemented; final verification blocked by sandbox environment.**

High-level summary of what was built:
- `server/src/app.ts` now exports a real `createApp()` (Express 5) with a single `GET /health`
  route. It issues a `fetch` against the hardcoded `http://host.docker.internal:11434` (a 2s
  `AbortSignal.timeout`), and responds `200` with `{ ok: true, ollamaReachable: boolean, ... }` —
  `ollamaStatus` on success, or an `error` message on failure/timeout. This replaces the ticket
  0.1 `placeholder` export in `server/` (that scaffolding's only job was proving the workspace
  wiring; this ticket gives `server/` its first real behavior, so the placeholder was removed from
  `server/` specifically — `shared/` and `extension/` keep theirs untouched, still Phase-1/2 work).
- `server/src/index.ts` is now the entrypoint: calls `createApp().listen(10105)`. Port is
  hardcoded to match PRD §4 / the ticket's compose port — ticket 0.3 owns making this
  config-driven.
- `server/test/index.test.ts` rewritten to start the app on an ephemeral port and hit `GET
  /health` with a real HTTP request (no mocking), asserting a `200` and a boolean
  `ollamaReachable` field. This exercises the real endpoint logic end-to-end without depending on
  Docker or a live Ollama instance — in this sandbox it correctly asserts the *failure* path
  (`ollamaReachable: false`) since nothing is listening on port 11434 here.
- `server/Dockerfile` added: `FROM node:22.16.0-slim` (matches `.nvmrc`), builds with the repo
  root as context (needed because `server` depends on `shared` via an npm workspace symlink).
  Copies each workspace's `package.json` first for layer caching, `npm ci`, then copies
  `tsconfig.base.json` + `shared/` + `server/` and runs `npm run build --workspace=server` (which
  transitively builds `shared` via the existing TS project reference — no separate build step for
  `shared` needed). Final `CMD ["node", "dist/index.js"]`, `EXPOSE 10105`.
- `docker-compose.yml` added at the repo root: single `server` service, `build.context: .` /
  `build.dockerfile: server/Dockerfile`, `ports: ["10105:10105"]`. No `extra_hosts` entry, per the
  ticket's explicit instruction (Docker Desktop for Windows resolves `host.docker.internal`
  natively).

Verification performed (server-level, outside Docker):
