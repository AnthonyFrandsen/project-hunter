# Phase 0.3 — Base Env-Var Config Loading

**Draft Number:** 4
**Ticket Status:** Done

## Goal
Give the server a single, consistent way to load its required configuration from environment variables before any pipeline logic depends on it.

## Description
Implement config loading for the following values, per PRD §8/§9. This ticket is the source of truth for these names and behaviors — downstream tickets (0.4's smoke test, Phase 1's auth check, Phase 11's setup doc) should reference this ticket rather than re-deriving them.

1. **Source resume path** — env var `HUNTER_RESUME_PATH`. Validation: the path must exist on disk and have a `.docx` extension.
2. **Output base folder path** — env var `HUNTER_OUTPUT_DIR` (where timestamped run folders are created). Validation: the folder must exist, or be creatable. Config loading itself creates the folder (`mkdir -p`-style) as a side effect of validation when it doesn't already exist — it doesn't just check creatability and defer the actual creation to whatever later code creates the timestamped per-run subfolders.
3. **Ollama endpoint** — env var `HUNTER_OLLAMA_ENDPOINT`. This is the base host:port only (e.g. `http://host.docker.internal:11434`) — it does not include the OpenAI-compat path suffix (e.g. `/v1`); that suffix is appended later by the Phase 4 code that calls it. Validation: the value must parse as a well-formed URL. This replaces the value ticket 0.2 hardcoded for its raw TCP reachability check — this ticket owns the config-driven replacement.
4. **Shared secret** (used for the auth check on incoming requests). Unlike the other three, this is **not** read from an environment variable. The server generates it at startup and prints it to the console, for the user to copy into the extension's configuration. It's exposed through the same shared config module as the other three values so Phase 1's auth-check code can read it, but it has no missing/invalid fail-fast case the way the other three do, since the server produces it itself rather than requiring it as input. The secret has no persistence: it is not written to disk, and every server restart generates and prints a fresh value, invalidating whatever secret the user previously copied into the extension. The user is expected to re-copy the newly printed secret into the extension's configuration after each restart.

Config should fail fast and clearly if a required value is missing or invalid, rather than failing silently deeper in the pipeline:
- On the **first** missing or invalid required value among the three env-var-backed ones (resume path, output dir, Ollama endpoint), the process logs a clear error and exits with a **non-zero status code**, before the Express server starts listening on port `10105`. Errors are not aggregated across multiple bad values in one run — first failure wins.

The "single shared module" in the Acceptance Criteria refers to a module within the `server/` package — not the `shared/` npm workspace from ticket 0.1 (which holds types common to `server/` and `extension/`). Config loading is server-internal and has no reason to be consumed by the extension.

## Acceptance Criteria
- [x] `HUNTER_RESUME_PATH`, `HUNTER_OUTPUT_DIR`, and `HUNTER_OLLAMA_ENDPOINT` are loaded from environment variables at startup.
- [x] Each is validated per the rules above: resume path exists and has a `.docx` extension; output dir exists (creating it if it doesn't); Ollama endpoint is a well-formed URL.
- [x] The shared secret is generated fresh at every startup and printed to the console — not read from an env var, and not persisted to disk between restarts.
- [x] On the first missing/invalid required value, the process logs a clear error and exits non-zero before the server starts listening — not a silent default or a later crash.
- [x] All four values (the three env-var-backed ones, plus the generated secret) are accessible to the rest of the server codebase via a single shared module (within `server/`).

## Implementation Log

**2026-07-28 — Implemented and verified.**

High-level summary of what was built:
- `server/src/config.ts` is the new single shared module. It exports a `Config` interface
  (`resumePath`, `outputDir`, `ollamaEndpoint`, `sharedSecret`), a `ConfigError` class, and a
  `loadConfig()` function. `loadConfig()` reads and validates the three env vars in a fixed order
  (resume path → output dir → Ollama endpoint), throwing `ConfigError` with a message naming the
  offending variable on the first failure — this gives the "first failure wins" behavior the
  ticket requires without needing any aggregation logic. Validation matches the ticket exactly:
  resume path must exist (`existsSync`) and end in `.docx`; output dir is created via
  `mkdirSync(value, { recursive: true })` (a no-op if it already exists, so "exists or is
  creatable" and "config loading itself creates it" are both satisfied by one call); Ollama
  endpoint is checked with `new URL(value)` inside a try/catch. The shared secret is generated
  with `randomBytes(32).toString("hex")` on every call — never read from `process.env`, never
  written to disk.
- `server/src/index.ts` calls `loadConfig()` through a small `loadConfigOrExit()` wrapper: on
  success it proceeds, on `ConfigError` (or any thrown error) it `console.error`s the message and
  calls `process.exit(1)` *before* `createApp(config).listen(PORT, ...)` is reached, satisfying
  "exits non-zero before the server starts listening." On success, the shared secret is printed to
  the console with an explicit instruction to paste it into the extension's configuration.
- `server/src/app.ts` no longer hardcodes the Ollama URL from ticket 0.2 — `createApp()` now takes
  a `config: Pick<Config, "ollamaEndpoint">` parameter and uses `config.ollamaEndpoint` in the
  `/health` handler's `fetch` call. This is the config-driven replacement the ticket calls out
  ticket 0.3 as owning.
- Tests: added `server/test/config.test.ts` covering the success path (all four values populated,
  shared secret non-empty and different across two `loadConfig()` calls), output-dir creation
  (both when missing and when already present), and one failure case per env var (missing, plus
  the resume-path `.docx`/existence checks and the Ollama URL well-formedness check), including an
  explicit test that a missing `HUNTER_RESUME_PATH` is reported even when the other two vars are
  also invalid, proving the fixed check order. Updated the existing `server/test/index.test.ts` to
  pass a `{ ollamaEndpoint }` object into `createApp()` now that it takes a config argument instead
  of using a module-level constant.

Verification performed:
- `npm run build --workspace=server`, `npm run test --workspace=server` (11/11 passing), and
  `npm run lint --workspace=server` all pass clean.
- Manually ran the built `dist/index.js` with all three env vars unset: it printed
  `HUNTER_RESUME_PATH is not set.` to stderr and exited with code `1`, confirming the fail-fast
  path works outside of the test harness too.
- Manually ran it again with all three env vars pointing at a fresh temp directory (output dir did
  not exist beforehand): it printed a shared secret, logged `server listening on :10105`, and the
  output dir was confirmed created on disk as a side effect — confirming the success path end to
  end, including the "config loading itself creates the folder" requirement.

Course corrections / blockers: none. The design followed the ticket as written — no open questions
were encountered during implementation. The only judgment call was the fixed validation order
(resume path, then output dir, then Ollama endpoint), which isn't specified in the ticket beyond
"first failure wins"; the order listed in the Description (§1, §2, §3) was used as the natural
tie-breaker, and a test pins this behavior so it doesn't drift silently later.
