# Phase 0.5 — Stubbed/Mocked Ollama Response Mode

**Draft Number:** 3
**Ticket Status:** Done

## Goal
Let development on Phases 1–3 (server core, extension scaffold, listing ingestion) proceed end-to-end without depending on the real Claude Code CLI + Ollama stack on every iteration.

## Description
Add a stub/mock mode that replaces the entire Claude Code CLI invocation in place of the real local model call — not merely a canned Ollama-style HTTP response. Per `docs/prd.md` §4, the real integration point is Claude Code CLI: it's spawned as a process, reads the source resume, calls the locally-served model via Ollama's OpenAI-compatible endpoint, and *drives file creation directly* (writing `.md`/`.docx` itself) — the server never calls Ollama's HTTP API and never writes those files itself. So the stub must fabricate that whole invocation, including the `.md`/`.docx` file writes a real run would produce, so callers see the same effects (files on disk, a response returned) whether the real CLI or the stub is underneath. This is also the seam Phase 4 will later swap the stub for the real CLI invocation at.

This lets the surrounding pipeline logic — queueing, progress reporting, file I/O — be built and tested before the real integration (Phase 4) is wired in.

The stub is not a single generic canned response: it returns response shapes keyed to which pipeline stage is calling it — e.g., a yes/no judgment and cleaned listing text for Phase 3's listing validation/cleaning (FR13/FR14), and tailored resume content for Phase 5's tailoring (FR15/FR16) — so each stage's downstream branching logic (e.g., the "not a valid listing" failure path in FR14) has something plausible to build and test against.

The stub also supports a configurable artificial delay, so the progress-reporting (FR4/FR26) and queue-depth (FR5) logic that Phase 1's status endpoint and Phase 2's popup polling are built against can be meaningfully exercised — an instantly-resolving stub would make multi-step progress and queue-depth states hard to observe or test during Phases 1–2.

This was raised as `docs/open-questions.md` OQ11. The user's full answer: "A stubbed mock Ollama call is a very suitable development scaffold for end-to-end testing before plugging the LLM calls into the application's logical flow." This confirms both that a stub mode is wanted, and its purpose — exercising the pipeline logic *around* the LLM call (queueing, progress, file I/O), not the LLM call's own behavior.

The toggle mechanism should follow the `HUNTER_*` env var naming convention established in ticket 0.3 (e.g. `HUNTER_MOCK_OLLAMA`); the exact name is an implementation detail left to the implementer, not a product decision needing sign-off. Likewise, how the stub is told which pipeline stage is calling it (and how the artificial delay is configured — fixed vs. per-call) are implementation details, not product decisions needing sign-off.

**Follow-up outside this ticket's scope:** answering OQ-A below (stub replaces the whole CLI invocation, not just the Ollama HTTP call) means ticket 0.4's smoke test — which only proves the server can reach Ollama's HTTP endpoint directly — doesn't actually validate the path this project depends on, since the server itself never calls Ollama; only the Claude Code CLI does. Ticket 0.4 should be reopened to instead verify that a Claude Code CLI invocation can reach the Ollama server on the Docker host. This doesn't block 0.5's own implementation and isn't part of its acceptance criteria — noted here since it surfaced from answering OQ-A.

## Implementation Log

**2026-07-29 — Implemented and verified.**

High-level summary of what was built:
- `server/src/claude-cli.ts` is the new seam module (the interface Phase 4's real spawn wrapper
  will also implement). It defines two discriminated stage shapes per the Description's example —
  `validate-and-clean-listing` (FR13/FR14: input is raw listing text, output is
  `{ isValidListing, cleanedListingText }`, with `cleanedListingText: null` on the invalid-listing
  branch so FR14's failure path has something concrete to branch on) and `tailor-resume` (FR15/FR16:
  input includes the cleaned listing, source resume path, output dir, base filename, and a 1-based
  `attempt`/optional `trimGuidance` pair for FR19's up-to-3-attempts trim/retry loop; output is the
  written `.md`/`.docx` paths). `createClaudeCliClient(config)` reads `config.mockOllama`: when true
  it returns the stub client; when false it returns a client whose `invoke()` always rejects with a
  "Phase 4 not implemented yet" error — this makes the toggle real today even though there's no real
  branch to swap in yet, and gives Phase 4 a clear, already-typed contract to implement against.
- `server/src/claude-cli-stub.ts` implements the actual fabrication. For the listing stage, it judges
  empty text (or text containing a `STUB_NOT_A_LISTING_MARKER` sentinel, exported for callers/tests
  that want to deliberately exercise the invalid-listing path) as invalid, and otherwise trims and
  whitespace-collapses the input as the "cleaned" text. For the tailor stage, it `mkdirSync`s the
  output dir and `writeFileSync`s a real `.md` file (readable Markdown referencing the listing
  excerpt, plus a trim-guidance note when `attempt > 1`) and a `.docx` file at the expected paths —
  the `.docx` is a plain-text placeholder, not a real OOXML document, since no `.docx` writer exists
  yet (that library choice is explicitly deferred to Phase 6 per `open-questions.md` OQ6) and nothing
  before Phase 6 needs to parse it as a real Word file; both files are clearly labeled as stub output
  in their content. A shared `sleep(delayMs)` runs before any stage responds, giving every call the
  same configurable artificial delay.
- `server/src/config.ts` gained two new optional, non-fail-fast fields: `mockOllama` (from
  `HUNTER_MOCK_OLLAMA`, true only for exactly `"true"` or `"1"`, default `false`) and
  `mockOllamaDelayMs` (from `HUNTER_MOCK_OLLAMA_DELAY_MS`, default `0`, `ConfigError` if set but not
  a non-negative integer). These follow the `HUNTER_*` convention from ticket 0.3 but deliberately
  don't participate in that ticket's "first missing/invalid required value" fail-fast ordering, since
  they're optional dev toggles, not required product config — they're read last in `loadConfig()`.
- `server/src/index.ts` logs a `console.warn` at startup whenever `config.mockOllama` is true,
  naming the stub file and stating it must never be enabled for a real run — a runtime-visible
  reinforcement of the "dev-only scaffold" requirement, on top of the written docs.
- Documented as dev-only scaffold (per the last acceptance criterion) in a new "Dev-only: stubbed
  Claude Code CLI mode" section in the root `README.md`, alongside the code comments in
  `claude-cli.ts`/`claude-cli-stub.ts` themselves.
- Tests: `server/test/claude-cli.test.ts` (new) covers the false-toggle rejection, both
  branches of the listing stage (valid text, empty text, and the sentinel-marker path), the tailor
  stage (files actually written to a temp dir with the expected content, including the
  attempt-2/trim-guidance variant), and the artificial delay (near-instant at `0`, measured elapsed
  time `>=` the configured value at `50`). `server/test/config.test.ts` gained cases for the two new
  env vars' defaults, valid values, and invalid-delay `ConfigError` cases.

Verification performed:
- `npm run build`, `npm run lint`, and `npm run test` (all workspaces, from repo root) pass clean —
  23/23 server tests (up from 11), no lint findings introduced (`biome check --write .` auto-fixed a
  handful of formatting/import-order nits in the new/edited files before the final clean run).
- Manual end-to-end check outside the test harness (mirroring how tickets 0.3/0.4 verified
  manually): ran `loadConfig()` + `createClaudeCliClient()` via `tsx -e` with
  `HUNTER_MOCK_OLLAMA=true` and `HUNTER_MOCK_OLLAMA_DELAY_MS=300` against a throwaway temp dir —
  confirmed the listing stage returned the expected shape after an observed ~300ms delay, and the
  tailor stage actually wrote `resume.md`/`resume.docx` to disk at the returned paths. Temp files
  removed afterward.

Course corrections / blockers:
- **No hardware/environment blocker.** This ticket only needed Node/TypeScript/Mocha inside the
  sandboxed Docker dev environment — it doesn't touch Docker Compose, the real Ollama endpoint, or
  the Claude Code CLI, so unlike tickets 0.4's smoke tests, nothing here required the real Windows
  host stack. Nothing to flag.
- One judgment call not fully dictated by the ticket: how the "invalid listing" branch gets
  deliberately triggered by a caller/test. The ticket only specifies the stub must give that branch
  "something plausible to build and test against," not a trigger mechanism. Implemented as: empty/
  whitespace-only text is judged invalid (a plausible real-world case), plus an explicit exported
  sentinel marker (`STUB_NOT_A_LISTING_MARKER`) callers can embed in test input to force the invalid
  path on demand. This is called out as a judgment call, not a product decision, consistent with the
  ticket's framing that stage-signaling/delay-configuration mechanics are implementation details.
- No other design changes were needed; the module structure (one interface module, one stub
  implementation module, wired through the existing `Config` object) followed directly from the
  ticket's description and ticket 0.3's existing config-module pattern.
