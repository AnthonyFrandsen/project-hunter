# Phase 0.1 — Repo Structure

**Draft Number:** 6
**Ticket Status:** Done

## Goal
Establish the baseline repo layout that the rest of Phase 0 (and every later phase) builds on top of.

## Description
Set up the monorepo skeleton as an **npm workspaces** project with clearly separated packages:
- Root `package.json` — declares the npm workspaces and orchestrates `install`, `build`, `lint`, and combined test automation across all packages from a single root command.
- `server/` — the Node/TypeScript/Express local helper server.
- `extension/` — the Chrome (Manifest V3) extension. Plain TypeScript compiled to JS is sufficient for now; a bundler (e.g., esbuild/Vite/webpack) is not needed at this scaffolding stage and is deferred to Phase 2, once actual extension logic (content scripts, etc.) is being written.
- `shared/` — a new workspace for object shapes/types common to `server/` and `extension/`, so the HTTP contract Phases 1 and 2 agree on is imported by both sides rather than hand-synced. `server/` and `extension/` consume `shared/`'s TypeScript source directly — there is no separate build/output step for `shared/` at this stage. The exact mechanism (TS project references, `tsconfig` path mapping, or plain relative imports) is left to the implementer's discretion.
- `docs/` — shared project documentation (this directory).

Tooling baseline for this pass:
- **Lint/format:** Biome, configured once at the repo root, with each of `server/`, `extension/`, and `shared/` having its own Biome config that extends the root config. The root `npm run lint` script delegates to each workspace's own lint script, so a workspace can layer on exceptions or added granularity without editing the shared root config. Whether `extension/`'s eventual `chrome.*` global overrides are added now as part of this scaffolding pass, or deferred until Phase 2 when actual extension logic starts using those globals, is left to the implementer's judgment — either is acceptable for this ticket.
- **Test framework:** Mocha is the established test runner for `server/`, `extension/`, and `shared/`. Assertions use Node's built-in `assert` module (no Chai or other assertion library). TypeScript test files run via a `tsx` register rather than a separate compile step. Each workspace has its own Mocha config extending a shared root config, mirroring the Biome per-workspace-extends-root pattern. No product logic exists yet, so this ticket only needs the wiring in place (Mocha installed and configured per workspace, root test script invoking each), not real test coverage.
- **Node/TypeScript versions:** whatever's current is acceptable for the main packages; the resolved current version is pinned at the repo level for reproducibility across contributors' machines. The exact pinning mechanism (`.nvmrc`, the `engines` field in root `package.json`, both, or a tool like Volta) is left to the implementer's discretion and is not a specified requirement of this ticket.
- **Out of scope for this pass:** CI configuration (e.g., a GitHub Actions workflow) and pre-commit enforcement of lint/format (e.g., husky + lint-staged) are both explicitly not needed at this scaffolding stage.

No product logic is expected yet — this is purely structural scaffolding so Phases 1 (server) and 2 (extension) have somewhere to live and can be developed in parallel once the HTTP contract between them is settled.

## Implementation Log

**2026-07-28 — Implemented and verified.**

High-level summary of what was built:
- Root `package.json` set up as an npm workspaces project (`shared`, `server`, `extension`), with `build`/`lint`/`test` scripts that each delegate via `npm run <script> --workspaces --if-present`. No custom root `install` script was added — a bare `npm install` at the root already installs all three workspaces, which is the idiomatic npm-workspaces behavior; defining a script literally named `install` would collide with npm's own lifecycle hook.
- `shared/` holds a single placeholder `PlaceholderContract` type, consumed by `server/` and `extension/` via plain package-name imports (`import type { PlaceholderContract } from "shared"`) resolved through the npm workspace symlink, backed by TypeScript project references (`shared` is `composite: true`; `server`/`extension` each add `"references": [{ "path": "../shared" }]` and build via `tsc -b`, which transitively builds `shared` with no separate root-level script needed to do so). All current usages of the shared type are `import type`-only, so nothing from `shared` is emitted into `server`'s or `extension`'s compiled JS yet — this sidesteps any bare-specifier module-resolution concerns for `extension`, which will run directly in a Chrome MV3 service worker with no bundler until Phase 2.
- `server/` and `extension/` each have their own `tsconfig.json` extending a shared root `tsconfig.base.json`; `server` compiles to CommonJS (Node), `extension` overrides to ES module output (`module`/`moduleResolution` for a real, unbundled MV3 service worker).
- Biome is configured once at the root (`biome.json`) with each workspace's `biome.json` using `"extends": ["../biome.json"]`; root `npm run lint` delegates to each workspace's own `lint` script (`biome check .`). Chrome-global overrides for `extension/` were deferred to Phase 2, per the ticket's explicit discretion, since no code touches `chrome.*` APIs yet.
- Mocha + Node's `assert` + a `tsx` register (`tsx/cjs`) are wired in all three workspaces, each with its own `.mocharc.json` extending a root `.mocharc.base.json`; one trivial placeholder test per workspace confirms the pipeline runs TypeScript tests directly with no separate compile step.
- Node version pinned via `.nvmrc` (`22.16.0`, matching the resolved current version) and mirrored in root `package.json`'s `engines.node`.
- Root `README.md` covers the project's aim/stack, the `server/`/`extension/`/`shared/` workspace layout, the root `build`/`lint`/`test` scripts, and a guide to the documents under `docs/`.
- Manifest V3 skeleton at `extension/manifest.json` (`manifest_version: 3`, background service worker pointing at compiled `dist/background.js`, `"type": "module"`). Kept intentionally minimal — host permissions, popup entry point, and notifications permission are Phase 2 concerns (roadmap item 2.1), not this scaffolding pass.

Blockers / course corrections encountered:
- **TypeScript 7 removed `moduleResolution: "node"` (the old "node10" classic resolver).** The initial `tsconfig.base.json` used it (reasonable at spec-writing time, but the installed toolchain — `typescript@7.0.2`, current as of implementation — had since dropped it). Corrected by moving the CommonJS-facing base config to `module`/`moduleResolution: "node16"` (TS's supported replacement, which behaves like classic Node resolution — including extensionless relative imports — for CJS files with no `"type": "module"` in `package.json`), and giving `extension/tsconfig.json` its own override (`module: "ES2022"`, `moduleResolution: "bundler"`) since MV3's real, unbundled ES-module service worker isn't a CommonJS consumer. This was purely a version-currency issue, not a design disagreement with the ticket.
- **Biome was initially linting/formatting compiled `dist/` output**, causing spurious "redundant `use strict`" and formatter-diff failures against generated `.js`/`.d.ts` files. Fixed by adding `"files.includes": ["**", "!**/dist/**", "!**/node_modules/**"]` to the root `biome.json` (inherited by all three per-workspace configs via `extends`).
- `npm install` originally reported 6 known vulnerabilities (1 low, 5 high) transitively via `mocha@11.7.6`'s own dependency tree (`glob`/`minimatch`/`brace-expansion`/`diff`/`serialize-javascript`). Several `mocha` versions were trialed chasing a clean audit: `11.3.0` (6 → 5, drops the `diff`/jsdiff advisory), then `8.1.3` at the user's request to check whether an older release was cleaner — it was not (7 vulnerabilities: 2 low, 5 high; reintroduces a `debug` ReDoS and `js-yaml` prototype-pollution/DoS that later 11.x releases had already fixed) — reverted back to `11.3.0`. Finally pinned to the `next`-tagged pre-release **`mocha@12.0.0-rc.5`**, which resolves the dependency tree entirely: **0 vulnerabilities** on a clean install.
  - Pinning to `12.0.0-rc.5` surfaced a real regression, not just a version bump: this RC's CLI has **dropped support for the `.mocharc.json` `extends` key** entirely (confirmed by grepping the installed package's CLI source — no `extends`-handling code remains), so every workspace's `npm run test` started failing with "No test files found" once each config's `"extends": "../.mocharc.base.json"` silently became a no-op.
  - Worked around it by replacing the JSON `extends` mechanism with plain JS composition: the shared root config is now `.mocharc.base.cjs` (`module.exports = { require: "tsx/cjs", spec: "test/**/*.test.ts" }`), and each workspace has a `.mocharc.cjs` that `require()`s the base and spreads it (`module.exports = { ...base }`). This preserves the "each workspace's Mocha config extends a shared root config" requirement in spirit and effect, just without relying on a feature this pre-release build doesn't currently implement. Confirmed working with a full clean-slate `npm install && npm run build && npm run lint && npm run test` — 0 vulnerabilities, all four commands pass.
  - Flagging for awareness: `12.0.0-rc.5` is a release candidate on Mocha's `next` dist-tag, not a stable release — its API/CLI behavior (as demonstrated by the dropped `extends` support) isn't guaranteed to match what ships in the eventual `12.0.0` stable. Worth re-checking the `.mocharc.cjs` composition (and whether `extends` support returns) once `12.0.0` is promoted to `latest`.
- No other course corrections. The npm-workspaces + TS project references + Biome/Mocha "extends" chain design held up as planned once the above two toolchain-version issues were resolved.

Verification performed: full clean-slate pass (`rm -rf node_modules */node_modules */dist */*.tsbuildinfo package-lock.json`, then `npm install`, `npm run build`, `npm run lint`, `npm run test` from the repo root) — all four succeeded with no errors, confirming the "repo builds/installs cleanly" criterion end-to-end, not just incrementally.
