# Phase 0.4 — Ollama Smoke Test

**Draft Number:** 4
**Ticket Status:** Done

## Goal
Prove the full boot-to-inference path works before building any real pipeline logic on top of it.

## Description
- Create a standalone script, committed to the repo, that sends a trivial prompt to Ollama's OpenAI-compatible endpoint using the base endpoint from `HUNTER_OLLAMA_ENDPOINT` (ticket 0.3). The script reads `process.env.HUNTER_OLLAMA_ENDPOINT` directly rather than importing ticket 0.3's config-loading module — this is an explorative, one-off diagnostic, so it doesn't need to duplicate or reuse the server's config-loading code, only to prove the cross-container call is feasible. This also means the script has no dependency on 0.3's module and nothing to keep in sync if that module changes later. The script is run manually/on-demand from within the Docker container, after the container has been successfully created — it is **not** triggered automatically on container boot, and it is not part of the server's startup procedure. This is distinct from ticket 0.2's `GET /health` endpoint, which only proves raw TCP reachability to `host.docker.internal:11434` on request — this ticket proves the actual OpenAI-compatible chat/completion path works.
- Model: `qwen3.5:4b`, per `docs/prd.md` §4 item 3 (confirmed real and already pulled on the host).
- The exact trivial prompt text is an implementation detail (e.g., a short fixed string) and doesn't need product sign-off.
- The script logs the response (or a clear failure) to the console so success/failure is easy to observe when it's run.
- The script owns its own OpenAI-compatible path-suffix construction (e.g., `/v1/chat/completions`) independently. It is not integrated with the server's logic, and Phase 4's later implementation of the same path-suffix logic is expected to duplicate rather than reuse this script's code.
- Because the script is not part of server startup, a failed smoke test never blocks or otherwise affects the Express server starting.
- This is a throwaway smoke test in spirit — a diagnostic tool to validate Phase 0.2's connectivity and Phase 0.3's config wiring together, not product functionality. Concretely, "throwaway" means: the script stays committed in the repo as an ad-hoc diagnostic (it is not deleted after first use), but it is never invoked automatically by boot, startup, or test flows — so it has no automated interaction with ticket 0.5's stub/mock Ollama mode.

## Implementation Log

**2026-07-28 — Implemented and verified against the real Windows host.**

High-level summary of what was built:
- `server/scripts/ollama-smoke-test.ts` is the new standalone script. It reads
  `process.env.HUNTER_OLLAMA_ENDPOINT` directly (no import of ticket 0.3's `config.ts`), builds its
  own path suffix (`${endpoint}/v1/chat/completions`), and POSTs a trivial one-line user prompt
  (`"Reply with exactly one word: pong"`) with `model: "qwen3.5:4b"` using a 30s
  `AbortSignal.timeout`. On success it logs the assistant's message content to the console and
  exits `0`; on a missing env var, non-2xx response, or thrown error (network failure, timeout,
  etc.) it logs a clear failure message via `console.error` and exits `1`. It lives outside
  `server/src`, so it isn't part of the `tsc -b` build or the Express app's dependency graph, and
  it's excluded from `server/tsconfig.json`'s `include` (same pattern as `server/test/`) — it's
  meant to be run directly via `tsx`, matching how this repo already runs TypeScript test files.
- Added a `smoke:ollama` script to `server/package.json` (`tsx scripts/ollama-smoke-test.ts`) as a
  convenience entry point — runnable as `npm run smoke:ollama --workspace=server` or, from inside
  the container, `npx tsx scripts/ollama-smoke-test.ts` from `/app/server`. `tsx` is already a root
  devDependency (used for the existing Mocha/TypeScript test setup), so it's present in the image's
  `node_modules/.bin` via the existing `RUN npm ci` step — no new dependency was added.
- No changes were made to `server/src/`, `Dockerfile`, or `docker-compose.yml` — this ticket is
  purely additive, as intended.

Verification performed (on the real Windows host, with Docker Desktop and native Ollama running —
not a sandboxed environment):
- Confirmed `qwen3.5:4b` is present via `curl http://localhost:11434/api/tags` (alongside
  `qwen3.5:2b/4b-q8_0/9b`), matching the model the PRD and this ticket specify.
- Unit-level sanity checks outside Docker: ran the script with `HUNTER_OLLAMA_ENDPOINT` unset
  (logged `HUNTER_OLLAMA_ENDPOINT is not set.`, exited `1`) and against a local mock
  OpenAI-compatible HTTP server (confirmed the exact request shape — `POST /v1/chat/completions`
  with the expected JSON body — and that a `choices[0].message.content` response is parsed and
  printed, exiting `0`).
- Real end-to-end run: built the image (`docker compose build server`), started a container with
  `HUNTER_OLLAMA_ENDPOINT=http://host.docker.internal:11434` (plus a throwaway `.docx` and output
  dir to satisfy ticket 0.3's other required env vars so the server itself would boot), confirmed
  the server logged `server listening on :10105`, then ran `docker exec hunter-smoke-test npx tsx
  scripts/ollama-smoke-test.ts` against the running container. Output:
  ```
  Sending smoke-test prompt to http://host.docker.internal:11434/v1/chat/completions (model: qwen3.5:4b)...
  Smoke test succeeded. Response:
  pong
  ```
  exited `0`, confirming the full boot-to-inference path (container → `host.docker.internal:11434`
  → Ollama's OpenAI-compatible endpoint → `qwen3.5:4b` → response) works end to end. Container and
  the associated Docker network created for this test were removed afterward; no state persists
  from the test.
- `npm run build`, `npm run test`, and `npm run lint` (all workspaces, from repo root) pass clean —
  11/11 server tests, no lint findings, including the new files.

Course corrections / blockers:
- Minor tooling friction, not a design issue: invoking `docker compose run` with `-e`/`-v` flags
  from Git Bash on Windows triggers MSYS's automatic Unix-path-to-Windows-path conversion, which
  mangled the container-side paths (e.g. `/tmp/resume.docx` silently became a Windows temp path).
  Worked around by exporting `MSYS_NO_PATHCONV=1` for that one command. This only affected the
  ad hoc manual verification run, not the script or any committed file — no code changes resulted.
- No design changes to the script itself were needed; it matches the ticket description as written
  on the first pass.
