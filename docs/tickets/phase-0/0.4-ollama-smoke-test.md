# Phase 0.4 — Ollama Smoke Test

**Draft Number:** 6
**Ticket Status:** Done — CLI-based check implemented and verified on the Windows host (see Implementation Log)

## Reopened (2026-07-29)
Ticket 0.5's refinement (OQ-A) established that the server never calls Ollama's HTTP API directly and never writes the output files itself — only the **Claude Code CLI** does, spawned as a subprocess that reads the source resume, calls Ollama's OpenAI-compatible endpoint itself, and drives `.md`/`.docx` file creation directly (`docs/prd.md` §4 item 3). That means the implementation below — a standalone script issuing its own `POST /v1/chat/completions` call straight from Node — validates that *some* process inside the container can reach `host.docker.internal:11434` and get a chat completion back, but it does not validate the actual dependency this project has: that a **Claude Code CLI invocation**, run the way Phase 4 will run it, can reach and successfully use the host's Ollama server from inside this container. Those are two different code paths to the same host port; proving one works says nothing about the other.

Per `docs/open-questions.md` OQ1 (sourced from `docs/prd-questions.md` Q25), the user has personally verified that the Claude Code CLI + Ollama command syntax works in principle (`ollama launch claude --model qwen3.5:4b -- ${prompt} -p --dangerously-skip-permissions`) — but that verification wasn't done from inside this project's Docker container against `host.docker.internal`, which is the environment Phase 4 will actually run in. This ticket is reopened to close that gap: swap the smoke test's mechanism from a raw HTTP call to an actual Claude Code CLI invocation, run inside the container, so the boot-to-inference path this project truly depends on is the one that's proven.

This does not roll back or invalidate ticket 0.2's `GET /health` check (raw TCP reachability) — it's still valid and still useful as a cheaper, faster first-line check. What's superseded is the assumption that a direct HTTP call from a script stands in for the Claude Code CLI's own path to Ollama.

## Goal
Prove the full boot-to-inference path works before building any real pipeline logic on top of it — specifically, that a **Claude Code CLI invocation** (the actual integration point per `docs/prd.md` §4 item 3), run inside the container, can reach and use Ollama on the Docker host. Reaching Ollama's HTTP endpoint directly from a script is a weaker property and is no longer sufficient to close this ticket.

## Description
- Add a new, separate script/procedure for this ticket rather than replacing the existing one: instead of issuing its own `POST /v1/chat/completions` call, it should invoke the **Claude Code CLI** the way Phase 4 intends to (per `docs/open-questions.md` OQ1 / `docs/prd-questions.md` Q25's confirmed command syntax — `ollama launch claude --model qwen3.5:4b -- ${prompt} -p --dangerously-skip-permissions`), pointed at the local Ollama-served `qwen3.5:4b` model via `HUNTER_OLLAMA_ENDPOINT` (ticket 0.3), and confirm it completes a trivial run successfully from inside the Docker container.
- Model: `qwen3.5:4b`, per `docs/prd.md` §4 item 3 (confirmed real and already pulled on the host).
- The script should still be run manually/on-demand from within the Docker container after the container has been created — it is **not** triggered automatically on container boot or server startup, and a failed run has no effect on the Express server. This part of the original design still holds.
- The script logs the CLI's output (or a clear failure) to the console so success/failure is easy to observe when it's run.
- Because the script is not part of server startup, it has no automated interaction with ticket 0.5's stub/mock Ollama mode (which replaces the CLI invocation only within the pipeline's own code paths, not this standalone diagnostic).
- Still a throwaway smoke test in spirit — a diagnostic tool, not product functionality — and stays committed in the repo as an ad-hoc diagnostic rather than being deleted after first use.
- **Container readiness is this ticket's own problem to solve ad hoc, not a prerequisite blocking it.** Whether the Docker image currently has the Claude Code CLI installed and available is unknown going in (ticket 0.2 explicitly deferred the CLI's working-directory volume mount to Phase 4). This ticket does not modify `Dockerfile` or `docker-compose.yml` to add the CLI — if it's missing, install/configure it manually inside the running container for the purposes of this test only. Whatever is learned about what the container is missing (packages, auth, mounts, config) must be written up in this ticket's Implementation Log so it can be turned into a follow-up ticket for making the CLI a proper part of the image — that write-up is this ticket's deliverable for that gap, not a silent workaround.
- **Scope boundary vs. Phase 4 item 4.1 (the real process-spawn wrapper):** this ticket proves the CLI can reach and successfully use Ollama from inside this container at all — it does not pre-build 4.1's spawn wrapper, error handling, or queue integration. Its value to Phase 4 is documentary: capturing the command syntax that actually works inside the container, any environment quirks, and any image gaps found along the way, so that later, functional implementation work has a proven starting point instead of starting from the unverified command syntax alone.
- The existing raw-HTTP-call script (`server/scripts/ollama-smoke-test.ts`) is kept as-is, unmodified — it remains a valid, cheaper first-line diagnostic for raw endpoint reachability, and there's no benefit to pruning it. The new CLI-based script/procedure added by this ticket is the authoritative check for "the real dependency path works"; the old script is not superseded, just narrower in scope.

**2026-07-28 — Implemented and verified against the real Windows host.**

High-level summary of what was built:
- `server/scripts/ollama-smoke-test.ts` is the new standalone script. It reads
  `process.env.HUNTER_OLLAMA_ENDPOINT` directly (no import of ticket 0.3's `config.ts`), builds its
  own path suffix (`${endpoint}/v1/chat/completions`), and POSTs a trivial one-line user prompt
  (`"Reply with exactly one word: pong"`) with `model: "qwen3.5:4b"` using a 30s
  `AbortSignal.timeout`. On success it logs the assistant's message content to the console and
  exits `0`; on a missing env var, non-2xx response, or thrown error (network failure, timeout,
  etc.) it logs a clear failure message via `console.error` and exits `1`. It lives outside
  `server/src`, so it isn't part of the `tsc -b` build or the Express app's dependency graph, and
  it's excluded from `server/tsconfig.json`'s `include` (same pattern as `server/test/`) — it's
  meant to be run directly via `tsx`, matching how this repo already runs TypeScript test files.
- Added a `smoke:ollama` script to `server/package.json` (`tsx scripts/ollama-smoke-test.ts`) as a
  convenience entry point — runnable as `npm run smoke:ollama --workspace=server` or, from inside
  the container, `npx tsx scripts/ollama-smoke-test.ts` from `/app/server`. `tsx` is already a root
  devDependency (used for the existing Mocha/TypeScript test setup), so it's present in the image's
  `node_modules/.bin` via the existing `RUN npm ci` step — no new dependency was added.
- No changes were made to `server/src/`, `Dockerfile`, or `docker-compose.yml` — this ticket is
  purely additive, as intended.

Verification performed (on the real Windows host, with Docker Desktop and native Ollama running —
not a sandboxed environment):
- Confirmed `qwen3.5:4b` is present via `curl http://localhost:11434/api/tags` (alongside
  `qwen3.5:2b/4b-q8_0/9b`), matching the model the PRD and this ticket specify.
- Unit-level sanity checks outside Docker: ran the script with `HUNTER_OLLAMA_ENDPOINT` unset
  (logged `HUNTER_OLLAMA_ENDPOINT is not set.`, exited `1`) and against a local mock
  OpenAI-compatible HTTP server (confirmed the exact request shape — `POST /v1/chat/completions`
  with the expected JSON body — and that a `choices[0].message.content` response is parsed and
  printed, exiting `0`).
- Real end-to-end run: built the image (`docker compose build server`), started a container with
  `HUNTER_OLLAMA_ENDPOINT=http://host.docker.internal:11434` (plus a throwaway `.docx` and output
  dir to satisfy ticket 0.3's other required env vars so the server itself would boot), confirmed
  the server logged `server listening on :10105`, then ran `docker exec hunter-smoke-test npx tsx
  scripts/ollama-smoke-test.ts` against the running container. Output:

  Smoke test succeeded. Response:

  exited `0`, confirming the full boot-to-inference path (container → `host.docker.internal:11434`

Course corrections / blockers:
- Minor tooling friction, not a design issue: invoking `docker compose run` with `-e`/`-v` flags
  from Git Bash on Windows triggers MSYS's automatic Unix-path-to-Windows-path conversion, which
  mangled the container-side paths (e.g. `/tmp/resume.docx` silently became a Windows temp path).
  Worked around by exporting `MSYS_NO_PATHCONV=1` for that one command. This only affected the
  ad hoc manual verification run, not the script or any committed file — no code changes resulted.

  on the first pass.

**2026-07-29 — Reopening closed: CLI-based smoke test implemented and verified on the Windows host.**

High-level summary of what was built:
- `server/scripts/ollama-claude-cli-smoke-test.ts` is the new standalone script this reopening
  required. It reads `HUNTER_OLLAMA_ENDPOINT` directly (same pattern as the existing script), then
  `spawn`s the `claude` binary as a subprocess: `claude -p "<trivial prompt>" --model qwen3.5:4b
  --dangerously-skip-permissions`, with `ANTHROPIC_BASE_URL` set to the endpoint,
  `ANTHROPIC_AUTH_TOKEN=ollama`, and `ANTHROPIC_API_KEY=""` in the child's environment. Stdout/stderr
  are captured and logged on completion; a 5-minute watchdog kills the process and reports a clear
  timeout failure rather than hanging indefinitely. Exit code mirrors the CLI's own (0 = success).
  Lives outside `server/src` and is excluded from `server/tsconfig.json`, matching the existing
  script's pattern — run via `tsx`, not part of the build or Express app.
- Added `smoke:ollama-cli` to `server/package.json` alongside the existing `smoke:ollama`, so it's
  runnable the same way (`npm run smoke:ollama-cli --workspace=server`, or from inside the container,
  `npx tsx scripts/ollama-claude-cli-smoke-test.ts` from `/app/server`).
- The env-var mechanism (`ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY`) was
  determined by checking Ollama's current published integration docs
  (`docs.ollama.com/integrations/claude-code`) rather than guessing from the ticket's example command.
  That doc clarifies what the ticket's example (`ollama launch claude --model ... -- ...`) actually
  is: `ollama launch claude` is a convenience subcommand of the **Ollama CLI itself** (not a
  documented Claude Code flag) that sets these three env vars and then execs `claude`. Recent Ollama
  versions serve the **Anthropic Messages API directly** at the server root — not routed through the
  OpenAI-compatible `/v1/chat/completions` path the PRD's wording assumed — so Claude Code talks to
  it like any other Anthropic-compatible provider, no proxy/shim involved. This smoke-test script
  calls `claude` directly with those three env vars rather than shelling out through `ollama launch`,
  since installing the separate `ollama` CLI inside the container just to use its wrapper (and
  pointing it at a remote host via `OLLAMA_HOST`) would add a second untested dependency for no
  behavioral difference — the env vars are the actual mechanism either way. This is a deliberate,
  documented deviation from the ticket's literal example syntax, not an oversight.
- `server/scripts/ollama-smoke-test.ts` (ticket 0.4's original raw-HTTP script) was **not modified**.
  It remains the cheaper, lower-level "can anything reach Ollama's HTTP endpoint" check; the new
  `ollama-claude-cli-smoke-test.ts` is now the authoritative check for "the real dependency path
  (Claude Code CLI → Ollama) works," per this ticket's reopening rationale.
- No changes were made to `Dockerfile` or `docker-compose.yml` — confirmed unmodified in this diff.

  env vars ticket 0.3 requires for the server to boot. Confirmed `fetch` to

  works identically, and that the missing-`HUNTER_OLLAMA_ENDPOINT` failure path (`unset
  HUNTER_OLLAMA_ENDPOINT` before running) prints a clear message and exits `1`, matching the existing

- `npm run build`, `npm run lint`, and `npm run test` (all workspaces, from repo root) pass clean —

**Image gap found — write-up for a follow-up ticket, per this ticket's scope boundary:**
The current `server/Dockerfile` has neither the Claude Code CLI nor a non-root user, and both are
required for the real Phase 4 spawn-wrapper integration (this ticket's diagnostic only worked around
both ad hoc, inside an already-running container, and did not touch the `Dockerfile` itself):
1. **Claude Code CLI is not part of the image.** `npm install -g @anthropic-ai/claude-code` after
   the fact worked fine and pulled in no surprising dependencies (Node 22/npm already present), but
   Phase 4's real spawn wrapper needs this baked into the image (or otherwise guaranteed present)
   rather than installed ad hoc per-container.
2. **The image has no non-root user.** Everything currently runs as root (`Dockerfile` never sets
   `USER`), which is directly incompatible with `--dangerously-skip-permissions` — the exact flag
   PRD §4 item 3 / `prd-questions.md` Q25–Q26 specify for the real integration. Phase 4 cannot spawn
   Claude Code as intended without the image running as (or being able to switch to) a non-root user.
   This also interacts with PRD Q26's Docker-mount confinement answer: whatever non-root user Phase 4
   settles on needs read/write access to the mounted working directory the real resume/output files
   live in.
3. Neither gap blocks this ticket (both were legitimately worked around ad hoc, as the ticket
   anticipated), but both should become explicit follow-up scope for Phase 4 item 4.1 rather than
   being rediscovered there from scratch.

Course corrections / blockers:
- The ticket's literal example command (`ollama launch claude --model qwen3.5:4b -- ${prompt} -p
  --dangerously-skip-permissions`) doesn't parse as a real invocation as written (flags after a bare
  positional prompt), and turned out to name an `ollama` CLI convenience subcommand rather than a
  `claude` invocation. Resolved by checking Ollama's current docs (see above) and implementing the
  equivalent, verified-working mechanism (`ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`/
  `ANTHROPIC_API_KEY` env vars + direct `claude` invocation) instead of the literal syntax — documented
  here rather than silently swapped in.
- The root-user failure (`--dangerously-skip-permissions cannot be used with root/sudo privileges`)
  was an unanticipated blocker, worked around ad hoc per this ticket's explicit instructions for
  container-readiness gaps, and written up above as follow-up scope rather than fixed permanently
  here.
- The initial 120s timeout was too tight for a cold-start model load and produced a false failure;
  raised to 5 minutes once the real (18s warm) latency was measured directly.
